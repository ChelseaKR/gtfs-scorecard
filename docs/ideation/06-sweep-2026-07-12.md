# Sweep 2026-07-12: demo readiness, then what to build next

A fresh pass with two questions. First, is the live service demo-ready today?
Second, what feature expansion is worth doing that the existing planning set
(FIX-01…13, EXP-01…17, RR:R1–R16, RR:E1–E14) does not already hold? The
demo-readiness answer is evidence from this morning; the ideas that follow are
net-new per this folder's rule, with existing IDs cited where an idea extends
one.

## Part 1 — Demo readiness

### Evidence reviewed

- **CI on `main` is green across the board.** The last push (2026-07-11,
  merge of #69) passed CI, E2E, Accessibility, CodeQL, security, OpenSSF
  Scorecard, Standards pin, and Deploy site.
- **The scheduled daily run is healthy.** Daily scorecard succeeded
  2026-07-11 14:33 UTC. Intraday refresh and Realtime monitor were green
  through 23:13 UTC that night (one intraday failure at 21:09 recovered on
  the next tick).
- **The test suite passes from a clean checkout.** 1,276 passed, 6 skipped,
  15 seconds.
- **One real soft spot: the deploy Lighthouse gate.** The manually
  dispatched Daily scorecard run at 19:49 UTC on 2026-07-11 failed the
  homepage performance assertion (score 0.63 against a 0.90 floor, LCP
  3,199 ms against 2,500, total blocking time 2,797 ms against 200) and the
  deploy job was skipped. This was about half an hour after the perf
  stabilization merges (#61, #64–66) landed, so either the gate still has
  run-to-run variance or fresh, larger data regresses the homepage in a way
  the code-path fixes did not cover. When this gate fails, prerendered pages
  keep serving the previous deploy while the S3 artifacts underneath refresh.
- **A visible polish wart on one generated page.** The adoption page
  committed 2026-07-10 (before the #69 registry dedupe) lists duplicate
  agencies and one garbled display name, an agency rendered as "24 hour
  advance reservations required". The dedupe should clear the duplicates on
  the next full render; the display-name hygiene is not yet checked anywhere.
- **Docs quote three different corpus sizes.** README says ~1,140 feed
  records, `feature-roadmap.md` says about 1,450, the adoption page says
  1,449. Each was right when written; none of them is generated.
- **Not verified from this environment:** the live site itself. This
  sandbox's egress proxy returns 403 for gtfsscorecard.org, so freshness and
  phone-load speed of the deployed pages rest on the green Deploy, E2E, and
  Accessibility gates rather than direct observation.

### Verdict

Yes, demo-ready, with two pre-demo checks. The core demo (a pilot agency
scorecard on a phone) is backed by green CI, a passing daily pipeline, and a
passing accessibility gate. Before a real café demo: open the homepage and
the adoption page on a phone over cell data. The first confirms the perf
gate failure was variance rather than a live regression; the second confirms
the dedupe reached the rendered pages. FIX-14 below turns that manual check
into something the pipeline enforces.

## Part 2 — Net-new fixes

Effort tiers as elsewhere in this folder: S ≈ days, M ≈ 1–2 weeks, L ≈ a
month, XL ≈ a quarter.

### FIX-14 — A deploy gate that cannot hold data hostage

**Status: Done (2026-07-12).** `pages.yml` takes a `perf_gate` input; the
data-refresh callers (`scorecard.yml`, `refresh.yml`) pass `advisory`, which
demotes every assertion except accessibility to a warning (derived from the
blocking config with `jq` at run time, so the two cannot drift) and surfaces
a miss as a workflow warning and run-summary note instead of a skipped
deploy. Code pushes keep the full blocking gate, now median of three runs.
Still open: the byte budget on homepage payloads as the blocking data-growth
signal.

**Pitch.** Separate the performance gate from the data-refresh deploy path so
a Lighthouse variance can never leave prerendered pages a day stale, and make
the gate's blocking signal one that actually moves with the moving input.

**Why it matters.** The 2026-07-11 dispatch showed the failure mode: gate
fails, deploy skipped, pages freeze at the previous render while S3 data
moves on. The site stayed presentable because the prior deploy was good, but
a second consecutive failure would push page staleness past a day, silently.
The moving input on a data refresh is data size, not code, and a synthetic
perf score is a noisy proxy for it.

**Shape of the work.** Keep the Lighthouse assertion blocking for code
pushes, run it median-of-three to damp variance. For data-only refresh
deploys, demote it to advisory and add a blocking budget on what actually
grows: bytes of JSON inlined into the homepage and the directory, tracked
against a stated ceiling. Route gate failures into the existing watchdog
alert rather than a silent skip, and record gate outcomes in the
run-summary surface FIX-11 proposes.

**Effort.** S.

**Risks and dependencies.** Loosening anything on the deploy path needs the
inverse guarantee stated and tested: a code change still cannot ship a perf
regression. Pairs naturally with FIX-11 but does not depend on it.

**Excellent looks like.** Two provable sentences: a data refresh is never
blocked by performance variance, and a code push is never deployed with a
performance regression. Plus an alert, not an absence, when either gate
trips.

### FIX-15 — Corpus numbers in prose come from one place

**Status: Done (2026-07-12), one simplification.** Shipped as
`pipeline/scripts/check_doc_stats.py` in `make verify`: every corpus figure
quoted in tracked docs must sit within 8% of the registry count, and a
reworded sentence that drops its figure out of the check fails too. The
simplification: the registry (`agencies.yaml`) is itself the always-current
source in git, so no intermediate `stats.json` is generated until something
other than this check consumes one. The two stale figures the check caught
on its first run (`product-roadmap.md`, `feature-roadmap.md`) were
refreshed.

**Pitch.** Generate the small set of numbers the docs love to quote
(registry count, published pages, RT-scored count, last full run date) into a
stats block at publish time, and add a CI check that flags drift between that
block and the numbers quoted in tracked docs.

**Why it matters.** Three documents currently disagree about how many feeds
the service tracks. Each number was true at writing; the registry moved. For
a product whose brand is honest measurement, stale self-description is the
cheapest credibility leak to close.

**Shape of the work.** Extend the FIX-03 pattern (generated presentation
constants) from code into prose: a `stats.json` written by the publish step,
a short list of tracked docs whose quoted figures must match it within a
stated tolerance, and a CI failure message that names the file and the fresh
number. README and roadmap docs switch to citing the generated figure.

**Effort.** S.

**Risks and dependencies.** None material. The tolerance keeps the check
from nagging on every daily fluctuation.

**Excellent looks like.** No number appears in a tracked doc that the
pipeline knows better than the author.

## Part 3 — Net-new expansions

### EXP-18 — The export diff: what changed in this feed version

**Status: Done (2026-07-12), retention solved sideways.** The raw-zip
retention this item waited on turned out unnecessary: `exportdiff.py`
remembers a compact structure fingerprint per agency (route ids and names,
stop positions, trip count, service end; a few KB of derived data in
`data/cache/structure/<agency>.json`, persisted through a private S3 cache
path). When the feed hash moves, the previous fingerprint is diffed
into bounded plain sentences ("Route 5 (E Street Express) is no longer in
the export", "12 stops moved more than 100 m") and rides on the artifact as
the additive `export_diff` block, rendered at the top of "What changed in
this feed". Best-effort in `run_agency`, never blocks a score; sentence
wording is pinned by tests.

**Delivery completed 2026-08-05.** The block now also rides the alert
channels the item asked for. `alerts.py` builds an `export_change` item per
agency whose latest run carries changes, rendered in its own digest section
and deliverable to webhooks through the existing `notify.py` path;
`atomfeed.py` carries `export_change` entries in both the site-wide feed
(via `render_site.compute_export_changes`, gated to the same
comparison-eligible cohort the grade-change entries use, so a duplicate feed
identity cannot announce the same change twice) and each agency's own feed.
The digest and feed copy never assert the grade held, because an export
change and a grade drop can land on the same run.

Still open: FIX-02's byte-exact archive remains the gated, stronger
substrate. Two deliberate non-extensions: `changes/latest.json` stays a
grade-or-score contract (see `docs/api.md`), and the public subscribe form's
kind list is unchanged.

**Pitch.** When a new feed version lands, tell the manager in plain language
what changed in the data itself: routes added or removed, stops that moved
past a threshold, the service span, days-per-week shape. EXP-02's grade story
narrates grade movement, and the shipped `feeddiff.py` diffs the quality
artifacts (findings appeared, cleared, moved); this narrates the feed
content itself, the layer both of those sit on top of.

**Why it matters.** The classic vendor-export accident is silent. A route
drops out of the export or forty stops shift, the validator finds nothing
wrong because nothing is invalid, and nobody notices until riders do. The
pipeline already fetches every version and records content hashes (the
FIX-01/FIX-02 provenance spine), so it is the one actor positioned to
notice.

**Shape of the work.** On a `feed_sha256` change, compute a bounded
structural diff between the previous and current zips: row counts by file,
route id set delta, stop position deltas over a distance threshold, service
span and weekly-pattern delta. Render as a short "This export changed" block
on the scorecard, and carry it in the Atom and webhook change feeds (extends
RR:E8 delivery). The tone stays descriptive; change is normal, and the block
must never read as an accusation.

**Effort.** M.

**Risks and dependencies.** Needs the previous version retained. FIX-02's
content-addressed archive makes this exact and is the right substrate, but a
rolling keep-latest-two copy is enough to start without waiting on the
FIX-02 S3 and license gates. Memory bounds for the largest feeds inside an
Actions runner need a measured ceiling.

**Excellent looks like.** A manager learns their export dropped a route from
the scorecard before a rider complaint reaches them, and golden tests pin
the diff wording the way render goldens already pin the scorecard.

### EXP-19 — Service alerts people can actually read

**Status: measurement half done (2026-07-12); any weight stays gated.**
`rt.parse_alerts` observes each alert's content (plain header text,
description, cause and effect, entity scoping, latest period end) and
`rt.alerts_content` summarizes the window's newest snapshot into the
category details. Two zero-deduction findings ship the fixes: alerts that
ended more than 30 days ago and are still served, and alerts with no header
text. The score is untouched by construction (a test pins that), and
`rubric.md` states the observed-not-scored status; a weighted sub-signal
would enter through the FIX-06 shadow-scoring path with a methodology
announcement, exactly as this item's risk note required.

**Pitch.** The realtime sampler already fetches `service_alerts` alongside
trip updates and vehicle positions, but only measures reachability and
header freshness. Score the content: does each alert carry plain header and
description text, a validity period, entity scoping, and has its period
already ended while it is still being served?

**Why it matters.** Alerts are the one GTFS-RT feed whose payload reaches
the rider's eyes verbatim. A detour notice that ended in May and is still
published in July teaches riders to ignore every future alert, which is the
exact trust this product exists to protect.

**Shape of the work.** Mechanical content checks over the alert snapshots
the sampler already captures: text presence and length, cause and effect
populated, active period sane against the sample time, informed entities
resolvable against the schedule feed. Surface as a small sub-signal inside
the existing Realtime category, with any weight change shadow-scored through
the FIX-06 canary before it takes effect. Fixes stay concrete: "2 alerts
ended more than 30 days ago and are still published; remove them in your
alerts tool."

**Effort.** M.

**Risks and dependencies.** Readability judgments must stay mechanical
(presence, length, staleness), never stylistic, and nothing model-generated
sits in the graded path. An agency with no alerts feed stays neutral, the
same rule the category already applies. Yolobus publishes all three RT
feeds and is the natural pilot proof.

**Excellent looks like.** `rubric.md` gains a cited alerts section, and a
pilot agency clears a stale alert because the scorecard named it.

### EXP-20 — Works in the field: offline-capable agency pages

**Status: Done (2026-07-12), one delta.** `web/sw.js` keeps the shell and
every visited page readable offline: navigations are network first (a deploy
can never be pinned by the worker), shell assets and artifact JSON are
stale-while-revalidate, tiles and images stay network-only so a phone's
cache stays small. `nav.js` registers the worker on every page and shows the
honesty note (`role="status"`) whenever the network is gone; unsaved pages
get a plain offline fallback instead of a browser error. Covered by
`tests/e2e/test_offline.py` with real airplane-mode reloads; the other e2e
contexts block service workers so Playwright route stubs keep working. The
delta: the install manifest (add-to-home-screen) is deferred until someone
asks to install it — offline reading needed no manifest.

**Pitch.** Make the site a small progressive web app: the shell and any
agency page a person has visited stay available offline, with a visible
"showing data from <date>" banner whenever the copy is cached.

**Why it matters.** The café demo and a liaison's rural site visit share a
failure mode, weak connectivity, and the product spec makes the phone demo a
hard requirement. Offline capability is that requirement wearing work
boots: the liaison walks into an agency office with the scorecard already
on their phone regardless of signal.

**Shape of the work.** A web manifest plus a service worker, cache-first for
the shell, stale-while-revalidate for artifact JSON. The offline banner is
the honesty primitive and is non-negotiable, in the RR:R8 spirit of stating
limits in the UI rather than in docs; artifact dates already exist to power
it. Cache versioned with the build so a deploy invalidates cleanly, and an
e2e case in the FIX-09 Playwright harness that loads a visited agency page
with network emulation off.

**Effort.** S–M.

**Risks and dependencies.** A service worker is a new deploy-time state to
manage; a bad one can pin users to an old build, which is why the cache key
follows the build id. Cached data must never present as current, hence the
banner. No dependency on other items.

**Excellent looks like.** An airplane-mode phone shows yesterday's Yolobus
scorecard with a dated banner, and the perf budgets of Part 1 do not move.

### EXP-21 — Are riders actually seeing this feed? A presence check

**Pitch.** RR:E2 proposes explaining trip-planner ingestion in human terms.
Go one step further and observe it where terms of service allow: for each
agency, check presence and recency in openly documented consumer-facing
indexes (Transitland's operator and feed API, the Transit app public
coverage endpoint, plus the OTP plannability sample `otp-qa.yml` already
runs) and render a sourced "where riders can see this feed" block.

**Why it matters.** The feared consequence behind every freshness metric is
being dropped by trip planners. Today the tool infers that risk from the
calendar (`google_gate.py` flags the four-week acceptance window) and checks
the feed's own liveness (`liveness.py`); it never observes the consumer-side
outcome. One sourced observation ("listed in Transitland as of July 8") is
worth a page of inference during an agency call.

**Shape of the work.** A weekly job querying only documented public APIs
with the project's standing etiquette, writing a per-agency presence block
with source name and checked-at date. Absence is framed neutrally: "not
found in X's public index; listings can lag." This block feeds RR:E2's
rider-facing surface rather than duplicating it.

**Effort.** M.

**Risks and dependencies.** Two declared gates. Google and Apple offer no
sanctioned check, so they are out of scope entirely rather than scraped.
The Transit app API terms need a read before any call is made. Copy needs
the same care the NTD flag got (RR:R7 precedent): no implication that any
app owes an agency a listing.

**Excellent looks like.** A liaison can say, with sources and dates on
screen, that the feed is reaching riders, and an agency that fixes an
expired feed watches the presence block recover.

## Suggested order

FIX-14 first, since it defends the demo the service is already giving every
day, and FIX-15 beside it as a same-week small. EXP-19 next: it is the
cheapest new rider-facing value because the data is already being sampled.
EXP-20 follows as a self-contained frontend piece. EXP-18 starts once the
keep-latest-two retention question is settled (or FIX-02's archive lands,
whichever is first), and EXP-21 waits on its terms-of-service read.

Same disclaimers as the rest of this folder: candidates for evaluation, not
commitments, and every gate above is declared to be honored, not worked
around.
